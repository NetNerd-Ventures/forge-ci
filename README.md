# forge-ci

Reusable GitHub Actions workflows and scripts for the forge deploy pipeline.
Consumers are generated by the `forge` Claude Code plugin; see
`docs/specs/2026-09-18-forge-ci-pipeline-design.md` there.

This repo holds no application code. It publishes six `workflow_call`
workflows, the scripts they run, two branch-ruleset templates, and a test
harness that lints and unit-tests everything before every push. Consumers
`uses:` the workflows at a pinned tag; nothing here runs against a
consumer's secrets or data except through the inputs/secrets a consumer
explicitly passes.

## Why this repo is public

Reusable GitHub Actions workflows can only be called from another repo in
the same GitHub Actions run's context when the *called* workflow's repo is
public, or when the calling repo has explicit access to a private one. To
avoid managing per-repo access grants for every consumer under
`NetNerd-Ventures`, this repo is public. Nothing secret lives in it: no
values, only secret *names* consumers must set, and the workflows never log
inputs that could carry a secret. Being public also means the workflow
source is auditable by anyone before a consumer wires it in.

## The `forge-ci-ref` rule

Every reusable workflow declares a required `forge-ci-ref` input. Each job
checks forge-ci out into `.forge-ci/` at that ref before running any script,
so a workflow always executes the scripts that shipped with the exact
`forge-ci-ref` it was called with — not whatever the caller's `@vN` tag
happens to resolve to at call time for supporting scripts, and not the
workflow file's own commit. Consumers therefore write the same ref twice:
once in `uses: .../gates.yml@v1` (which version of the *workflow* runs) and
once in `with: forge-ci-ref: v1` (which version of the *scripts* it checks
out). Keep both in sync; a probe repo confirmed GitHub resolves the `uses:`
tag independently of the input.

Every script under `scripts/` finds the consumer repo via `REPO_ROOT`
(default: the process's working directory), never via its own parent
directory, because it runs from the nested `.forge-ci/scripts/` checkout
with the consumer repo as the working directory.

## Check-run names and ruleset contexts

A check run produced by a called (reusable) workflow's job is named
`<caller job id> / <callee job name>`. The forge templates fix the caller
job ids to `gates` and `review`, so the check-run names a branch ruleset
must require are:

- `gates / typecheck`
- `gates / unit tests`
- `gates / migration drift`
- `gates / gitleaks`
- `gates / actionlint`
- `review / cross-model review` (two-tier only; see below)

`scripts/apply-rulesets.sh` renders and applies these automatically — see
"Ruleset script usage" below.

## Two modes

**Two-tier**: a `staging` integration branch feeds a `main` production
branch through `/promote`. Cross-model review is `required: true` — the
check goes red and blocks merge if a vendor model flags a problem, and
`promote.yml` opens the staging→main PR. Canonical example: the five
callers plus `promote.yml` under
`test/fixtures/consumer-two-tier/.github/workflows/`.

**Single-tier**: `main` is both the integration and production branch.
There is no `promote.yml` caller. Cross-model review is `required: false`
(the workflow's own `required` input flows into the script as
`--advisory`): the review still runs and still posts its sticky PR comment,
but the check never turns red and the step summary is labelled ADVISORY
instead of blocking. Canonical example: `test/fixtures/consumer-single-tier/.github/workflows/`.

Both fixture trees are real, valid caller workflows — `test/run.sh` and
`actionlint` lint them on every push (`.github/workflows/self-test.yml`),
so they stay in sync with the reusable workflows' actual inputs.

## Ruleset script usage

```bash
scripts/apply-rulesets.sh --repo owner/name --mode two-tier|single-tier \
  --integration <branch> --production <branch> \
  [--extra-gate <job name>]... [--dry-run]
```

Renders `rulesets/integration.json` (two-tier only) and
`rulesets/production.json` from the templates in `rulesets/`, filling in
the required-status-check contexts listed above (plus `review / cross-model
review` for two-tier, plus any `--extra-gate` names), and applies them with
`gh api` against `repos/<owner>/<name>/rulesets`. Idempotent: a ruleset
already named `forge-ci: <branch>` is updated (`PUT`) in place rather than
duplicated; a new one is created (`POST`). Single-tier adds the merge-queue
rule to the one ruleset it creates, since there is no separate integration
tier to queue into. `--dry-run` prints the rendered ruleset JSON and exits
without calling `gh`.

## Secrets

Org-level secrets (`gh secret set <NAME> --org NetNerd-Ventures --visibility
selected --repos <list>`), names only — values are never read or written by
anything in this repo:

- `FORGE_CI_APP_ID`
- `FORGE_CI_APP_PRIVATE_KEY`
- `FORGE_REVIEW_OPENAI_API_KEY`
- `FORGE_REVIEW_XAI_API_KEY`
- `FORGE_REVIEW_ANTHROPIC_API_KEY`

Per-repo secrets, set directly on the consumer repo:

- `DATABASE_URL`, scoped to the two GitHub Environments `staging-db` and
  `production-db` (single-tier consumers still need both environments;
  `migrate.yml` picks one by branch).
- `VERCEL_TOKEN`.

### Rotation

```bash
gh secret set <NAME> --org NetNerd-Ventures --visibility selected --repos <list>
```

Before rotating an org secret, check whether any consumer overrides it with
a per-repo fallback of the same name (a per-repo secret always wins over an
org one of the same name), by grepping that consumer's deviations:

```bash
jq '.deviations' <consumer-repo>/.forge/config.json
```

Any repo listed there for a secret name needs its own `gh secret set`
alongside the org rotation, or it will keep using its stale per-repo value.

## Tag policy

- `v1.x.y` (e.g. `v1.0.0`) is an immutable release tag — never force-moved.
- `v1` is a moving major tag, force-updated (`git tag -f v1 <vX.Y.Z>`) to
  point at the latest `v1.x.y` release. Consumers pin `uses: .../<workflow>.yml@v1`
  to always track the latest 1.x release, or pin an exact `@v1.x.y` to
  freeze.
